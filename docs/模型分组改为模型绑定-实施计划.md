# 模型分组改为模型绑定：实施计划

## 1. 目标

将当前“模型分组绑定供应商、供应商下全部模型自动获得权限”改为“模型分组直接绑定具体模型”。

目标权限链路：

```text
用户
  → 默认模型分组 + 管理员分配的用户分组
    → 分组直接绑定的模型
```

不再使用“分组 → 供应商 → 供应商下所有模型”作为用户模型权限来源。

---

## 2. 已确认产品规则

以下规则是本计划的约束，实施时不得擅自改变：

1. 用户可用模型是并集：
   ```text
   active 默认分组绑定的模型
   ∪
   管理员分配给用户的 active 分组绑定的模型
   ```
2. 系统只能有一个默认分组，不能同时存在多个默认分组。
3. 只有管理员可以创建、编辑、删除模型分组，以及给用户分配/修改模型分组。
4. 普通用户不能自行配置或修改分组。
5. 新增模型默认分配到当前默认分组。
6. “新增模型”包括所有真正创建 `ModelMapping` 的入口：手动创建、同步创建、批量创建、自动创建；更新已有模型不得重置已有分组关系。
7. 如果新增模型时没有默认分组，则不自动绑定任何分组。
8. 一个模型允许属于多个分组，一个分组允许包含多个模型。
9. 允许分组绑定 `disabled` 模型；但 disabled 模型不可出现在可用列表，也不可调用；重新启用后，如果仍在有效分组中则恢复可用。
10. 默认分组变更只修改 `is_default`，不自动补绑历史模型；以后新建模型绑定新的默认分组。
11. 取消默认分组不删除该分组已有的模型绑定；该分组仍可被管理员分配给用户。
12. “删除旧供应商”解释为删除旧的供应商-分组关联关系和相关代码，不删除 `providers` 供应商记录；供应商仍用于模型路由。
13. 不支持用户直接绑定模型，统一通过模型分组授权。
14. 暂时继续使用 `users.model_group_ids` JSON 保存用户分组，不在本次改造为 `user_model_groups` 关联表。
15. API Key 不保留独立模型分组权限；模型权限统一由默认分组和管理员分配给用户的分组决定。现有 API Key 分组关系需迁移/废弃/删除，不能继续形成第二套权限来源。
16. 普通用户不访问模型分组管理列表；普通用户通过经过权限过滤的模型列表接口获取可用模型。模型分组 CRUD 和用户分组分配均仅管理员可用。
17. 没有默认分组时允许系统处于无默认分组状态；用户仍可通过管理员分配的其他分组获得模型权限。后台可以继续显示无默认分组警告。
18. 供应商、模型分组、模型自身的 active/disabled 状态均参与最终可用性判断：分组、模型、供应商都必须 active 才能展示和调用。

## 4. 目标数据模型

### 4.1 新增模型分组-模型多对多表

新增表：`model_group_model_mappings`

字段：

```text
id           BIGINT 主键自增
 group_id     VARCHAR(32) → model_groups.group_id
 model_id     VARCHAR(50) → model_mappings.model_id
 created_at   DATETIME
```

约束：

```text
UNIQUE(group_id, model_id)
外键 group_id → model_groups.group_id，删除分组时级联清理关联
外键 model_id → model_mappings.model_id，删除模型时按最终删除策略处理
```

SQLAlchemy 目标关系：

```python
ModelGroup.model_mappings
ModelMapping.model_groups
```

### 4.2 删除旧供应商-分组关系

删除：

```text
provider_model_groups
ModelGroup.providers
Provider.model_groups
```

保留：

```text
providers
ModelMapping.provider_id
Provider 与 ModelMapping 的供应商关系
```

### 4.3 API Key 分组关系

本次需明确清理现有：

```text
api_key_model_groups
ApiKey.model_groups
相关 API Key 分组写入/读取/迁移代码
```

若数据库已有历史 API Key 分组数据，迁移时必须给出明确策略：本计划默认丢弃该独立权限来源，之后统一以 User 分组为准；如果发现现有业务确实依赖 API Key 级别限制，应在实施前停下并重新确认，不得静默改变线上权限。

## 5. 权限服务目标

在 `ProxyService` 中建立唯一模型权限查询入口，避免 `chat.py` 与 `proxy.py` 各自从供应商推导模型。

目标方法可以是：

```python
def get_effective_model_group_ids(self, user: User) -> Set[str]:
    """返回 active 默认分组与用户分配分组的有效集合。"""


def get_accessible_model_ids(self, user: User) -> Set[str]:
    """返回用户可访问的模型 ID 集合。"""


def get_accessible_model_mappings(self, user: User) -> List[ModelMapping]:
    """返回可展示/可调用的 active 模型映射。"""


def check_model_group_access(
    self,
    api_key: ApiKey,
    user: User,
    model_id: str,
) -> Dict[str, Any]:
    """按具体 model_id 校验用户模型权限。"""
```

最终判断必须满足：

```text
ModelMapping.model_id 属于用户有效分组绑定的模型
ModelMapping.status == active
所属 ModelGroup.status == active
所属 Provider.status == active
```

权限失败仍使用统一、不过度泄露内部结构的错误消息。

## 6. 数据迁移设计

### 6.1 迁移旧分组权限

旧关系：

```text
provider_model_groups:
  group_id → provider_id
```

迁移为：

```text
对于每个 group_id/provider_id：
  找到 model_mappings.provider_id == provider_id 的所有模型
  插入 group_id/model_id
```

迁移应使用唯一约束或 `INSERT IGNORE` 等等价方式避免重复。

### 6.2 迁移校验

迁移脚本或迁移后的验证必须检查：

```text
每个旧分组通过旧供应商关系推导出的模型集合
==
新模型分组关联表中的模型集合
```

如果发现找不到对应模型、重复关系或异常 group/provider，应记录并按实现时确定的失败策略处理；不得静默吞掉重要数据。

### 6.3 迁移后删除旧表

因为已确认旧供应商-分组关系迁移后直接删除，所以迁移完成且校验通过后：

```text
删除 provider_model_groups
删除相关 ORM 关系和代码
```

但不得删除 `providers` 表中的供应商配置。

### 6.4 用户 JSON 清理

删除模型分组时，需要同步清理所有用户 `model_group_ids` JSON 中的该 `group_id`，避免留下无效分组 ID。

## 7. 新模型自动绑定规则

所有真正创建 `ModelMapping` 的入口必须复用同一个辅助函数，例如：

```python
def assign_new_model_to_default_group(
    db: Session,
    model_mapping: ModelMapping,
) -> None:
    """将新模型绑定到当前唯一 active 默认分组；无默认分组则不绑定。"""
```

规则：

1. 查询唯一的 active 默认分组。
2. 新模型无论 active 或 disabled，都建立默认分组关联。
3. 没有默认分组则不建立关联。
4. 更新已有模型不得修改其模型分组关联。
5. 同步/自动创建流程不能因为重复同步而重置管理员手工调整的分组。

设置默认分组时只改变默认标记，不把历史模型批量加入该分组。

---

## 8. 默认分组唯一性

设置默认分组接口必须保证：

```text
同一事务内：
1. 将现有默认分组取消默认
2. 将目标分组设为默认
3. 提交
```

设置默认分组时：

- 目标分组必须存在。
- 目标分组必须 active。
- 允许从当前默认直接切换到另一个分组。
- 不自动补绑历史模型。

数据库唯一性可以通过应用事务保证；实施阶段应结合实际 MySQL 版本评估是否增加安全的数据库约束/辅助字段，不能创建会错误限制多个 `is_default=0` 记录的普通唯一索引。

## 9. API 设计目标

### 9.1 模型分组创建/更新

请求字段从：

```text
provider_ids
```

改为：

```text
model_ids
```

创建示例：

```json
{
  "name": "基础模型",
  "description": "普通用户可用模型",
  "is_default": 1,
  "model_ids": ["gpt-4o-mini", "claude-3-5-haiku"]
}
```

后端要求：

- model_id 必须存在。
- 去重。
- 不存在的模型返回 400，不得静默忽略。
- 允许绑定 disabled 模型。
- 绑定替换在事务中完成。
- CRUD 权限仅管理员。

### 9.2 模型列表

`/api/v1/chat/models` 和 `/api/v1/proxy/models` 必须只返回用户实际可访问、且模型/分组/供应商均 active 的模型。

删除当前 `/proxy/models` 中无授权模型时返回假模型的 fallback；无可用模型时返回空列表。

### 9.3 普通用户访问

普通用户不访问模型分组管理列表，不可创建/编辑/删除/分配分组；只通过权限过滤后的模型列表使用模型。

实施时必须检查实际路由挂载和前端菜单，确保没有只在前端隐藏、后端仍可写入的权限漏洞。

## 11. 测试计划

### 11.1 权限服务

至少覆盖：

1. 同一供应商的两个模型可以分别授权。
2. 用户只拥有绑定 `gpt-4o-mini` 的分组时，不能访问同供应商的 `gpt-4o`。
3. 一个模型属于多个分组时，拥有任一有效分组即可访问。

12. 没有默认分组时，新模型不自动绑定，但管理员分配分组后可用。
13. 默认分组切换不会自动补绑历史模型。
