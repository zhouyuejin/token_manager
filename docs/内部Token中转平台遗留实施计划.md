## 1. 目标与执行约定

将现有平台收口为主链路可用、权限一致、管理入口完整、验证结果可信的内部 Token 中转平台。后续按本文任务编号推进；原总计划保留设计和历史执行记录，本文记录剩余任务及最新验收结果。

任务分为三类：

- **必须修复或补齐**：已复现的回归、现有功能断链，以及当前计划明确要求的能力。
- **验证与交付**：代码已存在，但缺少真实联调、发布或运行验证。
- **待范围确认**：旧 PRD 与后续设计不一致，或协议扩展尚未明确支持边界。记录为遗留，不能默默删除，也不默认恢复已明确取消的设计。

执行规则：

1. 开始任务前复核当前代码、未提交修改、数据库目标及迁移版本；本文中的行号和测试数量仅作历史快照。
2. 涉及行为修改时，先构造失败测试，再做最小修复，最后验证完整调用路径；不得通过削弱断言、永久忽略测试或放宽权限换取通过。
3. 优先复用现有服务、表、页面、API 封装和测试工具，不新增一次性抽象或未经要求的依赖。
4. 数据库结构变更走 Alembic；业务数据和外部系统操作必须明确目标环境。测试使用隔离数据库、独立 Redis 命名空间，不清理业务库或共享缓存。
5. 按任务提交或交付，保留无关用户修改。完成一个任务后更新本文件的执行记录。
6. 分别记录“代码完成、验证完成、迁移完成、发布完成”。发布未获授权时停留在可交付状态，不把一次文档或代码任务当成上线授权。

## 4. Phase A：恢复主链路和验证基线

### A1：内容审计与账务字段边界

**代码依据：** [归因与用量记录](../backend/app/services/proxy_service.py)、[预扣服务](../backend/app/services/quota_reservation_service.py)、[预扣模型](../backend/app/models/quota_reservation.py)、[用量模型](../backend/app/models/usage_log.py)。

**已确认问题：** `capture_usage_attribution()` 新增 `content_audit_enabled`，调用方将字典通过 `**attribution` 展开到 `QuotaReservation`。模型没有该属性，因此报 `TypeError: 'content_audit_enabled' is an invalid keyword argument for QuotaReservation`。无 reservation 的部分 `UsageLog` 构造路径也会展开相同字典，需要一起验证。

**最小实现：** 显式区分项目/部门账务字段和内容审计控制元数据。模型构造只接收真实持久化字段；审计开关继续保留请求开始时的快照。不要为了接受字典而随意新增数据库列。

**失败测试与验收：**

- 审计开启/关闭时，代理和网页 Chat 的普通、流式调用均能预扣、结算、写用量。
- 无渠道、上游错误、客户端中断和结算失败路径能写入正确的失败记录并释放占用。
- 开启审计时只写脱敏摘要，关闭时不写正文或摘要。
- Responses、Embeddings、Images、Audio 的真实服务路径也经过验证，不能只 mock 掉预扣后宣称通过。
- 额度不重复扣减、预算不重复计费、失败请求不消耗额度。

**主要测试：** `test_content_privacy.py`、`test_quota_reservation.py`、`test_budget.py`、`test_proxy_protocols.py`、`test_project_attribution.py`。

## 5. Phase B：权限及密码功能闭环

### B1：RBAC 前后端一致

**代码依据：** [App.tsx](../frontend/src/App.tsx)、[MainLayout.tsx](../frontend/src/components/Layout/MainLayout.tsx)、[权限依赖](../backend/app/dependencies/__init__.py)、[角色页](../frontend/src/pages/admin/Roles.tsx)。

后端已有四种角色和权限表，前端管理路由及菜单仍只认 `admin`，导致部门管理员、审计员无法使用其授权页面。

| 角色 | 应实现的页面范围 | 操作边界 |
| --- | --- | --- |
| 平台管理员 | 全部已授权管理入口 | 管理读写 |
| 部门管理员 | 自己负责的部门及项目 | 不得越过部门归属 |
| 审计员 | 后端实际授权的管理只读页面 | 不展示写操作；直接 API 写请求仍拒绝 |
| 普通用户 | 个人统计、Key、申请、聊天、设置 | 仅本人或明确授权资源 |

**实施：** 建立最小统一权限映射并接入路由、菜单、页面依赖请求和按钮。若静态内置权限不能准确反映数据库权限，再增加当前用户有效权限读取接口。不能只放开路由，却让页面初始化调用无权访问的用户列表等接口。

角色页从静态说明提升为可核对的真实权限展示。原计划要求的权限编辑能力单列到 E2，尚未确认时不得让页面宣称可编辑。

**验收：** 覆盖四角色菜单、直接 URL、GET/POST/PUT/DELETE 和跨部门访问；前端限制与后端授权一致。审批负责人按现有业务授权处理，不能被一般后台权限重构破坏。

### B2：个人修改密码

**代码依据：** [Settings.tsx](../frontend/src/pages/Settings.tsx)、[用户 API](../frontend/src/api/users.ts)、[后端修改密码接口](../backend/app/api/v1/users.py)。

当前 `onPasswordChange` 只弹成功提示。补 API 封装和真实提交，遵循当前密码传输约定，校验失败展示真实原因，成功后清空敏感输入。

**验收：** 错误旧密码无法修改；成功响应后新密码可登录、旧密码不能登录；失败不显示成功；操作日志不含密码及哈希。密码存储方案变更由 E2 单独处理。

### B3：管理员重置密码

**代码依据：** [resetPassword 封装](../frontend/src/api/users.ts)、[用户管理页](../frontend/src/pages/admin/Users.tsx)、[管理员接口](../backend/app/api/v1/admin.py)。

当前前端封装指向不存在的 `/admin/users/{user_id}/reset-password`，且没有页面入口。补齐参数校验、后台接口、确认交互和操作日志，权限限定在实际具有用户管理写权限的角色。

**验收：** 无权限用户拒绝、不存在用户返回明确错误、重置后旧密码失效、新密码可登录、审计不泄露秘密。核对当前会话失效策略并记录其边界，不将“密码已修改”误写成“所有 access token 已撤销”。

## 7. Phase D：联调和运营验收

### D1：真实浏览器与业务闭环

使用隔离验收账号和项目完成以下流程并记录结果：

- Key 申请 → 审批 → 申请人一次性查看明文 → 实际代理 → 轮换/吊销/冻结状态反馈。
- 项目加入、模型分组和额度申请；拒绝、撤回、补充说明及通知。
- 预算配置 → 并发准入 → 实际结算/释放 → 阈值通知 → 超预算阻断。
- 成本筛选 → CSV 下载 → 明细及汇总与页面一致；失败不清空筛选。
- 对账正常、异常、运行中、失败四种状态及重跑；核验原计划要求的源 usage/reservation/quota 详情定位是否真正可用，而非只有 ID 文本。
- request_id 查询、路由说明、冷却状态、确认恢复及操作审计。
- 四角色权限、密码修改和告警配置。

优先使用可控模拟上游完成业务链路，真实渠道只做获授权的最小冒烟调用。浏览器构建验证不能替代以上交互验收。

### D2：真实 OIDC 联调

接入测试 IdP，验证首次建号、已验证邮箱绑定、重复登录、禁用账户、错误 issuer/audience/nonce/签名以及密码 fallback 开关。同步核对 Compose/部署环境是否实际传入 OIDC 配置，不能只在本机 `.env` 中存在。

**前置条件：** IdP 配置及测试账号可用；缺少配置时标记“等待联调条件”，不宣称已验收。不得将 client secret 写入文档或 Git。

### D3：内容审计性能

在同一受控环境比较开启/关闭摘要时的延迟和资源使用，覆盖长文本、嵌套 JSON、图片/音频 multipart。验证节点数和字符上限生效，二进制不进入摘要。记录样本量、机器配置和结果；若无明显退化，不额外引入缓存或队列。

### D4：健康、监控和灾备
